Why Evaluation Is a Testing Problem

A model that scores well on a benchmark can still fail the specific job you gave it. The useful question is not “is this model good?” but “does this system still do what it did last week, on the cases we care about?” That reframing turns evaluation into an engineering discipline with familiar tools: fixtures, coverage, regression gates, and CI.

LLM outputs are non-deterministic, so the assertions have to change even though the pipeline does not. Instead of exact-match checks, evaluation leans on scored rubrics, structural validation, and comparison against recorded baselines — then treats a score drop the same way a test suite treats a failing test.

How I Approach an Eval Harness

Stages of building an LLM evaluation harness and what each produces
Stage What it answers What it produces
Case collection Which real inputs matter, including the failures people actually reported? A versioned fixture set that grows with each bug found
Scoring design What does a correct answer look like for this task? Scoring scripts — structural checks, rubrics, and graded comparisons
Harness plumbing Can the system be driven the way a real client drives it? MCP-based tooling that exercises the system through its real interface
Baselines What was the score before this change? Recorded runs that make regressions visible
Pipeline integration Will a regression block the deploy? Automated QA pipelines running in cloud environments
Coverage review Which behaviors are still untested? The gap list that drove coverage from 40% to 70%+

Coverage is the metric I keep coming back to, because it is the one that predicts surprises. Raising it from 40% to 70%+ mattered less as a number than as a description of how much of the system's behavior was pinned down well enough that a change could not quietly break it.

MCP as Test Infrastructure

The Model Context Protocol gives an AI system a standard way to reach tools and data. That same interface is a natural test seam: if the harness drives the system through MCP, it exercises the real path production uses rather than a mock that drifts out of sync.

Building test infrastructure on MCP meant the tooling for Horizon Worlds and wearable-device systems could grow with the surface being tested instead of being rewritten each time a capability was added — which is what made a sustained coverage increase practical rather than a one-time push.
